# Research: Daml/Canton toolchain + ledger client for Collara (Windows, no Docker)

Date: 2026-10-01 · Machine: Windows 11 Pro 10.0.26200, 16 GB RAM (about 1.5 to 3 GB free during tests), 16 logical CPUs, Node 24.16.0, pnpm 11.13.0, Temurin JDK 21.0.12.1, Git Bash + PowerShell 5.1, no Docker. WSL2 Ubuntu 24.04 runs PostgreSQL 16.14.

Legend: **[VERIFIED]** means I ran it on this machine and observed the result shown. **[READ]** means it comes from an official doc, release note, registry or repository (URL given). **[INFERRED]** means my conclusion, which nobody tested.

Spike artifacts (all throwaway, safe to delete): `C:\Collara\.spike\` (`daml-hello`, `daml-keys`, `daml-multi`, `json-api`, `ts-client`, `multi-participant`, `sandbox-smoke.ps1`).

## 0. TL;DR

1. **Toolchain works on this Windows machine without Docker or admin rights.** **[VERIFIED]** It is **dpm 1.0.22 / Daml SDK 3.5.12** (latest stable, published 2026-09-24), which bundles **Canton 3.5.19** (open source), damlc / daml-script / codegen 3.5.3, and Daml-LF targets 2.1, 2.2 (the default), 2.3 and 2.dev. I installed it from the official zip with `dpm.exe bootstrap`, into `%APPDATA%\dpm`. Your user PATH is unchanged; scripts use a session-only PATH.
2. **`dpm build` / `dpm test`** passed, including `submitMustFail`, `trySubmit` and multi-party `actAs`. A deliberate authorization failure makes `dpm test` exit non-zero. **[VERIFIED]**
3. **`dpm sandbox --json-api-port 7575`** behaves as follows. **[VERIFIED]**
   - It is ready in about 36 to 52 s and uses about 1.0 to 1.6 GB RAM.
   - It runs protocol version **35** with in-memory H2 storage.
   - Over the JSON Ledger API v2 I ran: party allocation, DAR upload, create, exercise, ACS, updates (HTTP and WebSocket), completions, dedup, users and rights.
   - I also enabled HMAC JWT auth.
4. **Contract keys exist again in Canton 3.5 (LF 2.3) but are NOT unique.** **[READ + VERIFIED]** On both the IDE ledger and a real Canton 3.5.19 node, I created two active contracts with the same key and both commits succeeded. Collara must enforce "one active pledge per asset" by **consuming a single canonical control contract**. I also verified that pattern: two concurrent activations gave one commit and one `409 LOCAL_VERDICT_LOCKED_CONTRACTS`, and a retry gave `404 CONTRACT_NOT_FOUND`.
5. **Ledger client recommendation:** use **`openapi-fetch@0.17.0` plus types generated by `openapi-typescript@7.13.0` from the node's own `/docs/openapi` (Canton 3.5.19)**, in `packages/canton`.
   - `@canton-network/core-ledger-client@1.13.0` (Apache-2.0) also works against this node **[VERIFIED]**. It is a thin typed wrapper over the same `openapi-fetch`, but its types are a union of the 3.5.10 and 3.6.0 specs, it pulls 63 packages (wallet, splice, token-standard), and its README is empty.
   - Use `dpm codegen-js` (with `@daml/types@3.5.3`) only for template payload and choice types.
   - **`@daml/ledger` / `@daml/react` (2.10.6) are JSON API v1 / Daml 2.x only. Do not use them.**
6. **Splice LocalNet needs Docker Compose** and about 12 GB of container memory limits, so it is not runnable here. The substitute is **`dpm sandbox` plus an extra-participants config**, which gives 3 participant nodes on one synchronizer in one JVM (about 1.3 GB). **[VERIFIED]** Cross-participant privacy works there, and a joint `actAs` across participants is rejected. So Collara workflows must be propose/accept, not multi-controller single submissions.
7. **DLC-link Decentralization Manager v1.12.0 pins `sdk-version: 3.4.11` with `--target=2.2`.** **[READ]** Collara should therefore target **LF 2.2** (the SDK 3.5.12 default) so it can consume DM DARs as data-dependencies. **[INFERRED, not yet compiled]**

## 2. Installer: dpm vs legacy `daml` assistant

- **[READ]** https://docs.canton.network/sdks-tools/cli-tools/dpm.md says:
  - "`dpm` is the command-line interface for Canton development … Dpm runs on Windows, macOS and Linux."
  - Prerequisites: "JDK 17 or greater, installed and part of your `JAVA_HOME`".
  - It includes a migration section: remove `~/.daml/bin` from PATH and `rm -rf ~/.daml`.
  - Removed `daml` commands map to the Declarative API or JSON API: `daml ledger allocate-parties` → `POST /v2/parties`, `daml ledger upload-dar` → `POST /v2/dars`, `daml start` → `dpm sandbox` + `dpm build` + API calls.
- Windows options **[READ]**:
  - The GUI installer `https://get.digitalasset.com/install/latest-windows.html` redirects to `dpm-3.5.12-windows-amd64.exe` and "will install the dpm sdk and set up the PATH variable for you". **Not used**, because it modifies PATH.
  - Manual zip: `https://get.digitalasset.com/install/latest-windows-archive.html` → `.zip`, then `& "$EXTRACTED\windows-amd64\bin\dpm.exe" bootstrap $EXTRACTED\windows-amd64`. Optionally set `$env:DPM_HOME` / `$env:TMP` to user-owned directories first.
- **Doc discrepancy [VERIFIED]:** the docs say the Windows default `DPM_HOME` is `%APPDATA%/.dpm/`. The actual bootstrap wrote to **`%APPDATA%\dpm`** (no dot) and printed `Please add "C:\\Users\\Pongo\\AppData\\Roaming\\dpm\\bin" to your PATH`. **Bootstrap does not modify PATH.** I compared the user PATH before and after: unchanged.
- Layout after bootstrap **[VERIFIED]**:
  - `%APPDATA%\dpm\bin\dpm.cmd` is a shim: `C:\Users\Pongo\AppData\Roaming\dpm\cache\components\dpm\1.0.22\dpm.exe %*`.
  - `%APPDATA%\dpm\dpm-config.yaml` contains `registry: europe-docker.pkg.dev/da-images/public`.
  - `%APPDATA%\dpm\cache\components\<name>\<version>\…` holds the components (`canton-open-source/3.5.19/lib/canton-open-source-3.5.19.jar`, `damlc/3.5.3/damlc-dist-dpm/damlc.exe`, `codegen/3.5.3/binary.jar`, `daml-script/3.5.3/*.dar`, …).
- `dpm sandbox` is just `java -jar canton-open-source-3.5.19.jar sandbox …` (from the component's `component.yaml` `jar-commands`). `dpm canton-console` is `sandbox-console`.
- Old docs URLs under `docs.digitalasset.com/build/3.4|3.5/...` now return **404**. Current docs are at **docs.canton.network** (index: https://docs.canton.network/llms.txt). Old pages are at archived.docs.digitalasset.com.

### Windows-specific issues found [VERIFIED]
1. **Git Bash:** `dpm` resolves only as `dpm.cmd`, because bash ignores PATHEXT for `.cmd`. Use `dpm.cmd …`, define `alias dpm=dpm.cmd`, or call `…\cache\components\dpm\1.0.22\dpm.exe`. That last path is version-specific, so prefer `dpm.cmd`. In PowerShell `dpm` works as-is.
2. **PowerShell 5.1:** `curl` is an alias of `Invoke-WebRequest`, so use `curl.exe`. Native-arg quoting of inline JSON is broken in 5.1, so use `Invoke-RestMethod -Body (… | ConvertTo-Json -Depth 20)` or `curl.exe --data-binary "@file.json"`.
3. **PowerShell 5.1:** `[IO.File]::ReadAllText("relative")` resolves against the process CWD, not `Set-Location`, so always use absolute paths in scripts.
4. dpm/damlc write progress to stderr. PowerShell 5.1 wraps it as `RemoteException`/`NativeCommandError` noise, but the exit code is still correct (`$LASTEXITCODE`).
5. **Line endings:** CRLF in `.daml` and `daml.yaml` builds fine.
6. **Paths with spaces:** a project in `C:\Collara\.spike\with space\hello` builds fine. The JDK path with spaces is fine.
7. **Stopping the sandbox:** it is a process tree `dpm.cmd → dpm.exe → java.exe`. Kill it with `taskkill /PID <dpm pid> /T /F` (Git Bash: `taskkill //PID … //T //F`). Killing only the shell leaves java running. In-memory state is discarded, which is expected.
8. **Sandbox logs** go to `log\canton.log` relative to the working directory. Override with `--log-file-name log/xyz.log`.
9. **JVM heap:** dpm does not add `-Xmx`. Set `JDK_JAVA_OPTIONS=-Xmx1g`; the java launcher echoes `NOTE: Picked up JDK_JAVA_OPTIONS: -Xmx1g`. The sandbox help mentions `JAVA_OPTIONS`/`JAVA_OPTS`, but those only apply to Canton's own launcher script, not to dpm's `java -jar`.

## 3. Project format, build, test, sandbox

### daml.yaml (SDK 3.5.12) [VERIFIED]
Recommended Collara layout is multi-package, so the contracts DAR does not drag `daml-script` onto the ledger. The compiler warns about this: "This package defines templates or interfaces, and depends on daml-script … Uploading this package to a ledger will also upload daml-script … `-Werror=template-interface-depends-on-daml-script`".

`daml/multi-package.yaml`
```yaml

  - ./contracts
  - ./tests
```
`daml/contracts/daml.yaml`

name: collara-spike-contracts
source: daml
version: 0.0.1
dependencies:
  - daml-prim
  - daml-stdlib
build-options:
  - -Werror=template-interface-depends-on-daml-script

### Spike contract (`C:\Collara\.spike\daml-hello\daml\Main.daml`) [VERIFIED builds]
```haskell
template Asset with issuer : Party; owner : Party; name : Text where
    signatory issuer
    observer owner
    choice Transfer : ContractId Asset with newOwner : Party
      controller owner
      do create this with owner = newOwner
    nonconsuming choice Inspect : Text with viewer : Party
      controller viewer
      do pure name

template AssetControl with registrar : Party; borrower : Party; assetId : Text where
    signatory registrar
    observer borrower
    choice ActivatePledge : ContractId Pledge with lender : Party
      controller borrower, lender                      -- joint authority
      do create Pledge with registrar; borrower; lender; assetId

template Pledge with registrar : Party; borrower : Party; lender : Party; assetId : Text where
    signatory registrar, borrower, lender
    choice Release : ContractId AssetControl
      controller lender
      do create AssetControl with registrar; borrower; assetId
```

### Daml Script 3.5.3 API facts [READ from the shipped `daml-script-2.3.dar` sources, `Daml/Script.daml` export list]
- Submits: `submit`, `submitWithOptions`, `submitMustFail`, `submitMustFailWithOptions`, `submitResultAndTree`, `submitTree`, `submitWithError`, `trySubmit`, `trySubmitResultAndTree`, `trySubmitTree`.
- Options (Monoid `SubmitOptions`): `actAs`, `readAs`, `disclose`, `discloseMany`, `prefetchKeys`, `concurrently`.
- Legacy (still exported): `submitMulti [actAs] [readAs]`, `submitMultiMustFail`, `submitTreeMulti`, `trySubmitMulti`. `submitWithDisclosures` / `trySubmitConcurrently` are `DEPRECATED`.
- Queries: `query`, `queryInterface`, `queryContractId`, `queryInterfaceContractId`, `queryByKey`, `queryContractKey`, `queryNByKey`, `queryAllByKey`, `queryFilter`, `queryDisclosure`.
- Parties and users: `allocateParty`, `allocatePartyWithHint`, `allocatePartyByHint`, `allocatePartyOn …`, `listKnownParties`, plus user management and `submitUser`.
- Time: `getTime`, `setTime`, `passTime`, `sleep`.
- `SubmitError` constructors for asserting failure *reasons*: `ContractNotFound`, `ContractKeyNotFound`, `AuthorizationError {authorizationErrorMessage}`, `DuplicateContractKey`, `UnhandledException`, `UserError`, `TemplatePreconditionViolated`, `WronglyTypedContract`, `ContractDoesNotImplementInterface`, `LocalVerdictLockedContracts`, `UpgradeError`, `FailureStatusError`, …
- `concurrently`: its doc comment says "The submission order of transactions within `concurrently` is deterministic, this function is not intended to test contention". **Real contention must be tested against a sandbox**, as I did in §4.
- `dpm test` runs on the in-process "IDE ledger". `dpm script --ledger-host … --port … --dar … --script-name …` runs a script against a live node **[READ, sandbox doc]**.

### Interfaces, disclosure, multi-party
- **Interfaces:** supported in LF 2.x. SDK templates include `daml-intro-interfaces`; JS codegen emits `ToInterface` types; JSON API `ExerciseCommand.templateId` may be an interface id **[READ]**. DM's `GovernableAction` is an interface.
- **Explicit disclosure:** works in Daml Script **[VERIFIED]**. Over JSON: `JsCommands.disclosedContracts[] = {createdEventBlob (required), templateId?, contractId?, synchronizerId?}`. Get `createdEventBlob` from ACS or updates with `includeCreatedEventBlob: true`; I observed a 744-char blob **[VERIFIED fetch; JSON submission with disclosure not exercised]**.
- **Multi-party submission:** `actAs` and `readAs` are arrays in `JsCommands`.
  - On a single participant, `actAs:[Bob, LenderA]` works **[VERIFIED]**.
  - Across participants, it is rejected **[VERIFIED]** with `NO_SYNCHRONIZER_ON_WHICH_ALL_SUBMITTERS_CAN_SUBMIT`.
  - With JWT auth, the token's user must hold `CanActAs` for every `actAs` party (403 otherwise) **[VERIFIED]**.

### Sandbox [VERIFIED]
- **Real flags in 3.5.19** (from `dpm sandbox --help`, which prints the Canton jar help): `--ledger-api-port`, `--admin-api-port`, `--json-api-port`, `--sequencer-public-port`, `--sequencer-admin-port`, `--mediator-admin-port`, `--canton-port-file`, `--static-time`, `--dar`, `--dev`, `--multi-sync`, `-c/--config <files>`, `-C key=value`, `--log-file-name`, `--log-level-*`, `--bootstrap`.
  - **Docs discrepancy:** the doc page lists `--port`, `--port-file`, `--json-api-port-file` and `--shutdown-stdin-close`. Those belong to the older wrapper and are not in 3.5.19's help.
- Defaults: Ledger API gRPC 6865, Admin 6866, sequencer public 6867, sequencer admin 6868, mediator admin 6869. **JSON API is off unless `--json-api-port` is given.** 7575 is the convention. All bind to `127.0.0.1`.
- Node names: participant `sandbox`, `sequencer1`, `mediator1`, synchronizer alias `synchronizer-1`. Storage is in-memory H2 (`jdbc:h2:mem:…`). User management is enabled. A default user `participant_admin` exists.
- **Readiness:**
  - `GET /v2/version` and `GET /livez` return 200 early, before the synchronizer is connected.
  - `GET /readyz` returns `503 "[-] ledger failed (NOT_SERVING)"` until the participant is connected.
  - The **ports file** (`--canton-port-file`) is written last, after `Canton sandbox is ready.` is printed. Its content: `{"sandbox":{"ledgerApi":6865,"adminApi":6866,"jsonApi":7575}}`.
  - Gate scripts on the ports file, or on `/readyz` being 200.

- **`--dar` is incompatible with auth.** With auth on, the sandbox bootstrap's `upload-dar` was rejected with `PERMISSION_DENIED … Claims do not authorize the use of administrative services`, and the **sandbox process exited** (exit code 2). Upload the DAR afterwards with an admin token (`POST /v2/dars`), or use the declarative API.

Keycloak's default 5-minute access tokens fit.
- No token, wrong secret, or wrong `aud`: **HTTP 401** with an opaque body (`{"code":"NA","cause":"A security-sensitive error has been received",…,"grpcCodeValue":16}`). The real reason is only in the server log.
- `GET /v2/version`, `/livez`, `/readyz` and `/docs/*` need no token **[VERIFIED for /v2/version; READ for others]**.
- `participant_admin` token: upload DAR, allocate parties, create users. All 200.
- A user created with `CanActAs` for its party can submit as that party. `userId` may be **omitted** from the body, in which case it is taken from the token. `GET /v2/authenticated-user` returns the user.
- The same user submitting `actAs` for a party it lacks rights for gets **403**. Reading the ACS of a party it lacks rights for gets **403**. Listing all parties (`GET /v2/parties`) as a non-admin gets **403**.
- WebSocket with auth: subprotocols `["jwt.token.<JWT>", "daml.ws.auth"]` worked. A bounded request (`endInclusive`) closed with code 1000.
- Token format **[READ]** (https://docs.canton.network/appdev/deep-dives/authorization.md):
  - Audience-based tokens: `aud` = `https://daml.com/jwt/aud/participant/<participantId>` (or a configured `target-audience`), `sub` = user, `iss` = IDP id (empty or omitted for the default IDP).
  - Scope-based tokens (`scope: "daml_ledger_api"`) are **deprecated since 3.5.1**; scope-based access tokens are slated for removal in 3.7 (3.5.1 release notes).
  - Production: `type = jwt-jwks, url = …/jwks.json, target-audience = …` (Keycloak).
  - **Use `target-audience`.** The participant id changes on every sandbox restart, so per-participant audiences are impractical locally.

## 4. Contract keys and uniqueness

**[READ]** Canton 3.5.1 release notes (released May 27, 2026), https://docs.canton.network/global-synchronizer/release-notes/canton-releases/3-5-1.md:
> "The keys are not unique, meaning multiple contracts may share the same key. Negative lookups are not validated."
> "Contract keys are available from Daml-LF 2.3 onwards, which itself is available from Protocol Version 35."
> lookupByKey / fetchByKey / exerciseByKey act on "the first contract" … "lookupNByKey … looks up up to n contracts associated with the passed key." Order: "first the contracts created within a transaction, starting with the most recent, then explicitly disclosed contracts, then contracts known to the participant in recency order."

Under LF 2.2 (the default), any `key` declaration fails to compile with "contract Keys not supported on current lf version (2.2)". The fix is `build-options: [--target=2.3]` ([forum, 2026-08-06](https://forum.canton.network/t/dev-environment-seems-stuck-in-lf-2-2-no-matter-how-i-install/9048)). The older archived page says "Unique contract keys are not planned be supported in Canton 3.x" (https://archived.docs.digitalasset.com/build/3.5/reference/daml/contract-keys.html).

**[VERIFIED] Non-uniqueness proof**, with `C:\Collara\.spike\daml-keys` (`--target=2.3`, `key (registrar, assetId) : (Party, Text)`, `maintainer key._1`):
- IDE ledger: `trySubmit` of a second `Control` with the same key returned `Right`, and `queryNByKey @Control r 10 (r,"A1")` returned 2. Result: `test_keys_not_unique: ok, 2 active contracts, 2 transactions.`
- Real Canton 3.5.19, PV35 (`POST /v2/dars` of the LF 2.3 DAR returned `{}` HTTP 200): two `CreateCommand`s gave two 200s, both with `"contractKeyHash":"ryF7LWOCvcY+sxYjt1OT/gqGdAox2VCz3c8+9co/F84="`. ACS then showed 2 active `Control` contracts with key `(Registrar, A1)`.

**Recommended uniqueness pattern for Collara.** **[VERIFIED mechanics; design is INFERRED]**
- Keep one **canonical control contract per registered asset**, created only by a trusted registrar (signatory). `ActivatePledge` (or the step that creates the lock) is a **consuming** choice on that exact contract and creates the `Pledge` / lock atomically. A second activation must reference the same contract id, so it must fail.
  - On a real node, two parallel `submit-and-wait` calls (LenderA vs LenderB) returned one `200 {"updateId":…,"completionOffset":37}` and one **`409 LOCAL_VERDICT_LOCKED_CONTRACTS`**: `"cause":"Rejected transaction is referring to locked contracts "`, `errorCategory: 2`, `grpcCodeValue: 10`, `retryInfo: "1 second"`.
  - Retrying the loser after the winner committed returned **`404 CONTRACT_NOT_FOUND`**.
- Release recreates the control contract, as `Pledge.Release` does in the spike.
- Prevent "replacement control" bypass by making the registrar the only party able to create control contracts. Put duplicate screening off-ledger in the registrar's backend (document this as a trust assumption). Do not expose generic create paths.
- Do **not** use LF 2.3 keys for invariants. If keys are used at all, they are only a lookup convenience, and they force LF 2.3 / PV35 (see §8).

### Command dedup, change ID, offsets [VERIFIED + READ]
- Change ID = `(userId, actAs as a set, commandId)`. `submissionId` distinguishes retries of the same change.
- Resubmitting the same change ID, with the same or a different `submissionId`, returns **HTTP 409**:
```json
{"code":"DUPLICATE_COMMAND","cause":"Command submission already exists.","context":{"changeId":"ChangeId(collara-spike,spike-create-001,Set(Alice::…))","completion_offset":"17","accepted":"true","definite_answer":"true","existingSubmissionId":"Some(sub-0001)",…},"errorCategory":10,"grpcCodeValue":6}
```
  This is what an "unknown outcome" reconciler needs: `accepted:"true"` plus `completion_offset` tells you the original committed. Then fetch it with `POST /v2/updates/update-by-offset` or find it in completions.
- Default dedup period when omitted: **`PT168H` (7 days)**, as echoed in error contexts (`deduplicationPeriod: {duration: 'PT168H'}`). `deduplicationPeriod` is a oneOf: `{"DeduplicationDuration":{"value":{…Duration…}}}`, `{"DeduplicationOffset":{"value":<int64>}}`, or `{"Empty":{}}`.
- [Ledger API services doc](https://docs.canton.network/sdks-tools/api-reference/ledger-api-services.md) **[READ]**: "A command resubmission will generate a rejection until the original submission was rejected … or until the effective deduplication period has elapsed … Command deduplication is only *guaranteed* to work if all commands are submitted to the same Participant Node."
- **Offsets** are int64, absolute and per-participant. Docs: "An offset is meaningful only in the context of its original Participant Node … Different Participant Nodes associate different offsets to the same change". Offsets are causal per synchronizer. `GET /v2/state/ledger-end` returns the participant's head (0 means empty). `OffsetCheckpoint` updates (emitted at most every 75 s per `/v2/version`) give a safe resume offset even when no visible transactions occur. `GET /v2/state/latest-pruned-offsets` gives the lower bound for resumption.

- pnpm 11 note: installing `tsx` printed `[ERR_PNPM_IGNORED_BUILDS] Ignored build scripts: esbuild@0.28.2` and wrote `pnpm-workspace.yaml` with `allowBuilds: esbuild: set this to true or false`. tsx still ran. Set `allowBuilds` explicitly in the monorepo.

### Daml payload types: `dpm codegen-js` [VERIFIED]
- `dpm codegen-js .daml\dist\daml-hello-0.0.1.dar -o <dir> -s daml.js` takes 3.2 s.
- It emits one npm package per DAR package (`@daml.js/daml-hello-0.0.1`, plus a stdlib/prim package for each dependency), linked with `file:` deps. `package.json`: `"version": "3.5.12"`, `"description": "Generated by \`dpm codegen-js\` from SDK 3.5.12"`, deps `@mojotech/json-type-validation ^3.1.0`, peer `@daml/types 3.5.12` (not on npm, so use 3.5.3).

## 7. Splice LocalNet vs plain sandbox

- **LocalNet [READ]** (https://docs.canton.network/sdks-tools/development-tools/localnet.md):
  - "LocalNet provides a straightforward topology comprising three participants, three validators, a PostgreSQL database, and several web applications (wallet, sv, scan) behind an NGINX gateway". Validators are `app-provider`, `app-user` and `sv`.
  - It is part of cn-quickstart (`make setup && make build && make start`) and is "built from modular Docker Compose layers". **Docker is mandatory.**
  - Ports: `4xxx` sv / `3xxx` provider / `2xxx` user, with suffixes 901 ledger API, 902 admin, 975 JSON API, 903 validator admin. For example, the App Provider JSON API is at `localhost:3975`. Optional Keycloak, PQS, Grafana.
  - Splice repo `cluster/compose/localnet/resource-constraints.yaml @ 0.8.4`: canton `mem_limit: 4g` (`-Xmx2560m`), splice `3g`, postgres `2g`, console `2g`, plus about 2 GB of UIs and nginx, so **about 12+ GB** of limits. Images come from `ghcr.io/digital-asset/decentralized-canton-sync/docker/`, Postgres `14.24-trixie`.
  - **Not runnable on this machine:** there is no Docker on Windows or WSL, and only about 3 GB of RAM was free.
- **Plain `dpm sandbox` can host many parties on one participant: yes [VERIFIED].** Caveats:
  1. One participant operator sees everything, so it is not a privacy boundary between organizations. Ledger API filtering plus user rights under JWT give per-party API isolation **[VERIFIED 403s]**.
  2. Joint-controller choices work with `actAs:[a,b]` from one submitter. This hides cross-organization authorization issues that appear on a real network.
  3. There are no Canton Coin, wallet, Scan or traffic features (not needed by Collara).
  4. State and identities reset on restart.
- **Multi-participant without Docker [VERIFIED]:** `dpm sandbox -c extra-participants.conf …` with
```hocon
canton.participants.participant2 { storage.type = memory, admin-api.port = 6876, ledger-api.port = 6875,
  ledger-api.user-management-service.enabled = true, http-ledger-api.port = 7576 }
canton.participants.participant3 { storage.type = memory, admin-api.port = 6886, ledger-api.port = 6885,
  ledger-api.user-management-service.enabled = true, http-ledger-api.port = 7577 }
```
  - (I wrote it with newline-separated keys; see `C:\Collara\.spike\multi-participant\extra-participants.conf`.) The sandbox bootstrap script connects *every* local participant to `synchronizer-1`. Output: `participant3 listening at ports: 6885(gRPC) and 7577(HTTP)` / `participant2 … 7576` / `sandbox … 7575` / `Canton sandbox is ready.` The ports file lists all three. Ready in 54 s; 1.26 GB working set with `-Xmx1536m`.
  - Upload the DAR to **each** participant (`POST /v2/dars` on 7575/7576/7577, all 200).
  - Allocate Registrar on :7575, Borrower on :7576, LenderA on :7577. `GET /v2/parties/{Registrar}` on :7576 returns `isLocal:false`, so the party is known through topology.
  - Registrar creates `AssetControl(borrower=Borrower)` on :7575 → 200. ACS on :7576 shows 1 contract. **ACS on :7577 shows 0**, so privacy holds across participants.
  - A joint `ActivatePledge` submitted on :7576 with `actAs:[Borrower, LenderA]` is rejected:
```json
{"code":"NO_SYNCHRONIZER_ON_WHICH_ALL_SUBMITTERS_CAN_SUBMIT","cause":"Not connected to a synchronizer on which this participant can submit for all submitters","context":{"participant":"participant2","unknownSubmitters":"List(Borrower::…, LenderA::…)",…}}
```
  - **Design consequence [INFERRED]:** every Collara choice should have a single controlling organization per submission. Model borrower/lender joint steps as propose → accept, so the lender accepts a borrower-signed proposal and the acceptance consumes the control contract. Do not use `controller borrower, lender`.
  - This config is also a candidate for the BitSafe 2-of-3 demo topology (3 participants). It is not tested with DM.

## 8. Risks, conflicts, open items

1. **DM SDK mismatch.** Decentralization Manager v1.12.0 builds with SDK **3.4.11**, LF **2.2**, and depends on `splice-util-0.1.4.dar`. Collara on SDK 3.5.12 can presumably consume those DARs via `data-dependencies` (both LF 2.2), and a Canton 3.5.19 participant accepts LF 2.2 packages **[INFERRED, not compiled yet]**. Next step: build DM v1.12.0 DARs with `dpm install 3.4.11` (works offline from the OCI registry), then add them as data-dependencies to a Collara package built with 3.5.12. If that fails, pin Collara to SDK 3.4.11 (Canton 3.4.x sandbox, PV34).
2. **Do not adopt LF 2.3 / keys.** Keys are non-unique and require PV35. A network on PV34 (any 3.4 node, or a 3.5 node configured for PV34) would reject LF 2.3 DARs **[INFERRED from release notes]**.
3. **Sandbox state is ephemeral and identities rotate on restart.** The worker's offset checkpoints and the DB party mappings become invalid after a restart. Either reseed on every start (recommended for the MVP; detect it via `participantId` change or ledger-end < checkpoint), or configure Postgres storage. Postgres storage is untested; note that WSL Postgres is reachable from Windows only via the WSL IP here.
4. **`--dar` with auth enabled kills the sandbox.** Upload DARs through the API with an admin token.
5. **JWT TTL cap of 300 s** (`max-token-lifetime`). The API must refresh tokens; core-wallet-auth `AuthTokenProvider` caches until expiry.
6. **Doc and CLI drift.**
   - Sandbox flags `--port` vs `--ledger-api-port`.
   - `DPM_HOME` default `%APPDATA%\.dpm` (docs) vs `%APPDATA%\dpm` (actual).
   - The `/v2/commands/completions` endpoint is deprecated in favour of `/v2/commands/command-completions`.
   - Several `/v2/updates/*` endpoints say "will be removed in 3.5.0" but are still present in 3.5.19.
   - Always check the node's own `/docs/openapi`.
7. **core-ledger-client churns weekly** and targets 3.5 and 3.6 type unions. Pin the exact version (no caret) if used.
8. **Resources:** about 1.1 to 1.6 GB per sandbox JVM, and C: has about 15 GB free after install (the SDK uses 2.7 GB). The full stack (Next.js, Fastify, worker, sandbox, MinIO, Keycloak) on this machine needs memory budgeting. Use `-Xmx1g` for the sandbox.

## 9. Recommendations for the Collara build

1. **Toolchain pin.**
   - `sdk-version: 3.5.12` in every `daml.yaml`.
   - Explicit `build-options: [--target=2.2]` (`-Werror=template-interface-depends-on-daml-script` on the contracts package).
   - Multi-package layout `daml/collara/{contracts,tests}` (plus a separate `scripts` package for seeding if needed).
   - Document `%APPDATA%\dpm\bin` as a session PATH entry in `scripts/env.ps1` and `scripts/env.sh` (Git Bash uses `dpm.cmd`).
2. **Local ledger.** `infra/canton/` holds:
   - `sandbox.conf`: auth via `unsafe-jwt-hmac-256` + `target-audience`; optional extra participants.
   - Scripts `ledger-up.ps1` / `ledger-up.sh` that set `JDK_JAVA_OPTIONS=-Xmx1g`, start `dpm sandbox --json-api-port 7575 --canton-port-file …`, and wait for the ports file.
   - A seed step that uploads the DAR, allocates the parties (Demo Manufacturer, Demo CNC Dealer, Demo Verifier, Demo Lender A, Demo Lender B, Demo Auditor, Registrar/Operator) and creates one ledger user per org, with `CanActAs` only for its own party. It writes the mapping to Postgres.
   - Run demo fixtures through real commands.
   - Optional "3-participant mode" for governance.
3. **Client.**
   - `packages/canton` = `openapi-fetch@0.17.0` + `openapi-typescript@7.13.0` types generated from the pinned 3.5.19 spec (commit the spec), plus codegen-js `.d.ts` or Zod schemas for Collara templates.
   - Thin adapter functions: `submit(changeId, commands)`, `submitForTransaction`, `acsPage`, `updatesPage`, `completions`, `allocateParty`, `uploadDar`, `ensureUser`.
   - Use package-name template ids `#collara-contracts:Module:Template`.
   - `@canton-network/core-ledger-client@1.13.0` is an acceptable drop-in if the team prefers it; it is verified compatible with 3.5.19.
4. **Command lifecycle** (maps to PREPARED → SUBMITTED → COMMITTED → PROJECTED):
   - Persist `commandId` (deterministic per idempotency record) and `submissionId` (new UUID per attempt) before calling `submit-and-wait` (or `submit-and-wait-for-transaction`).
   - On timeout or 5xx, mark the command unknown and reconcile by resubmitting the same change ID: `409 DUPLICATE_COMMAND` with `context.accepted:"true"` and `completion_offset` means it committed. Alternatively reconcile through `/v2/commands/command-completions` from the stored ledger-end.
   - Treat `409 LOCAL_VERDICT_LOCKED_CONTRACTS` (retryInfo 1 s) as retryable contention.
   - Treat `404 CONTRACT_NOT_FOUND` after contention as a definite business rejection ("already activated").
   - Treat `400 DAML_AUTHORIZATION_ERROR` as a definite rejection.
5. **Worker projection.**
   - Bootstrap with `/v2/state/active-contracts-page` at `ledger-end`, then loop `/v2/updates/get-updates-page` from the stored `highestPageOffsetInclusive` (or a WebSocket on `/v2/updates`).
   - Use `TRANSACTION_SHAPE_LEDGER_EFFECTS` when choice and exercise evidence is needed for audit; otherwise use ACS_DELTA.
   - Store checkpoints per `(participantId, party-set)`. Apply events idempotently keyed by `(updateId, nodeId)`. Persist `OffsetCheckpoint` offsets.
   - Detect a sandbox reset (participantId changed or ledger-end < checkpoint) and reseed.
6. **Daml design.**
   - Canonical control contract consumed by activation (verified race-safe), with a registrar-only creation path.
   - Propose/accept for every cross-organization step.
   - No contract keys.
   - Use explicit disclosure or observer-based sharing contracts for scoped lender and auditor access. Prefer observers on purpose-built "share" contracts, so access is visible on-ledger and revocable by archive.
