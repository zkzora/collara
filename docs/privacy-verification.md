# Ledger privacy verification (five participants)

What was run to check **witness-level** privacy between organisations on the ledger, with the observed results, and
what this does **not** show. Synthetic data only. Nothing here is a production-readiness or security claim.

- Date: 2026-10-03 (local time; run ids are UTC). Authoring machine: Windows 11, Node 24.16.0, PostgreSQL 16.14 (WSL),
  SeaweedFS 4.48.
- Ledger: Canton 3.5.19 `dpm sandbox` with **five participant nodes in one JVM** (one sequencer, one mediator,
  in-memory storage, `unsafe-jwt-hmac-256` auth), started with `LOCALNET_JDK_JAVA_OPTIONS=-Xmx1536m`. Ready in 41 to
  54 s; java.exe working set about 1.6 GB right after start.
- Code: HEAD `cc7f777` plus the uncommitted changes of this task (5-participant mode, bootstrap placement, the
  privacy test).
- Test: `apps/api/test/localnet/privacy/witness.privacy.test.ts` (helpers in `evidence.ts`), opt-in with
  `PRIVACY_IT=1`, config `apps/api/vitest.privacy.config.ts`.
- Recorded runs: `2026-10-02T18-35-12-435Z` and `2026-10-02T18-39-30-685Z`, each on a freshly started sandbox:
  **7/7 tests, 80/80 checks** both times, with identical projections per node (apart from the order of one witness
  list). The tables below are from the second run. Two earlier runs failed for
  test-side reasons, fixed before the recorded runs (see [Findings](#findings) F10, and the note under it).
- Evidence: raw JSON in `.local/privacy/<run>/` (git-ignored); compact summary in
  [`docs/evidence/privacy-summary.json`](evidence/privacy-summary.json).

## How to reproduce

Prerequisites: DARs built (`dpm build --all` in `daml/collara`), PostgreSQL (`pnpm db:up`), SeaweedFS
(`pnpm infra:seaweed start`; the seed uploads synthetic documents). About 2.5 minutes once the sandbox is ready.
The test refuses to run on a sandbox with another number of participants.

PowerShell 5.1 (repo root):

```powershell
node scripts/localnet/down.mjs
$env:LOCALNET_JDK_JAVA_OPTIONS = "-Xmx1536m"; node scripts/localnet/up.mjs --participants=5
$env:PRIVACY_IT = "1"; pnpm --filter @collara/api test:privacy
# back to the normal single-participant sandbox
node scripts/localnet/down.mjs; node scripts/localnet/up.mjs --bootstrap
```

Git Bash (repo root):

```bash
node scripts/localnet/down.mjs
LOCALNET_JDK_JAVA_OPTIONS=-Xmx1536m node scripts/localnet/up.mjs --participants=5
PRIVACY_IT=1 pnpm --filter @collara/api test:privacy
node scripts/localnet/down.mjs && node scripts/localnet/up.mjs --bootstrap
```

The recorded runs used `npx vitest run --config vitest.privacy.config.ts --reporter=default` inside `apps/api`
(the same as the `test:privacy` script). Add `LOCALNET_IT_LOG=1` to see bootstrap and seed progress.

## What the test does

1. **One isolated world** (`bootstrap --prefix pv-…`, its own database) runs the real workflow:
   - the §7 seed (B1–B8, M1–M18, 24 steps, with documents), through the API's workflow runner;
   - the walkthrough W1–W14 through the **API routes** with demo sessions: review (start, save valuation USD
     150,000.00, submit, approve) → proposal FP-001 (principal USD 100,000.00, `termMetadata`
     `Synthetic 36-month terms`, `externalLegalRef` `LEGAL-DEMO-FP-001`) → accept → authorize → activate → release
     request RR-001 → reject → RR-002 → authorize → audit grants AG-001 (owner) and AG-002 (lender);
   - an auditor JSON export, generated by the worker's export handler in-process;
   - X1–X3, a second asset-level verification round (VR-002 → `VR_AcceptAssignment` → `VR_IssueAttestation`,
     ATT-002) through the runner, to measure fetch-only informees step by step.

   Every command is submitted by the acting organisation's own ledger user on its own participant
   (`LedgerSubmitRequest.source`, recorded as `commands.ledger_source`). Before and after every walkthrough and X step
   the test records every participant's ledger end, once all five have stopped moving.
2. **Readers created for the run** (by `participant_admin`):
   - per party: `<prefix>-pv-<Hint>` with **CanReadAs that party only**, on the party's participant;
   - per participant: `<prefix>-pv-node` with **CanReadAsAnyParty**, the operator's view of everything the node stores
     (`filtersForAnyParty`).
3. **Evidence** is raw JSON Ledger API data, never API or UI output: `POST /v2/updates` from offset 0 to the final
   ledger end with `TRANSACTION_SHAPE_LEDGER_EFFECTS` and a wildcard template filter (per party and per node);
   `POST /v2/updates/update-by-id` on every node for the key transactions; `POST /v2/updates/update-by-offset` for every
   offset that carries no visible transaction.
4. **Term markers** searched in every created argument, choice argument and exercise result: the principal and the
   valuation as exact decimal values (`100000.00`, `150000.00`), and the `termMetadata` and `externalLegalRef` texts.
5. **Revocation race** in two more worlds (each: main seed, then review → proposal → accept → authorize through the
   API; `apps/api/test/localnet/financing-fixture.ts`).

## Revocation race (daml-model.md §8.2)

`Control_Activate` does not read the `AttestationDisclosure`; the API checks it in `prepare()` before submitting.

| Variant | What happened | Result |
|---|---|---|
| Deterministic interleaving (world `pvr-…`) | The API route `POST /api/cases/CL-001/pledge-activation` ran with the real `prepare()` (including `requireActiveAttestationDisclosure`, which passed). The test wrapped the runner so that, after `prepare()` returned and before submission, the owner's `AttDisc_Revoke` committed (lender's disclosures at submission: 0) | **`Control_Activate` committed** (HTTP 200, `COMMITTED`, PL-001); 1 active lock, 0 disclosures. On Lender A's participant the revocation is at offset 202 and the activation at 204 |
| Unsynchronised (world `pvc-…`), one attempt | The activation route and the owner's revocation were submitted concurrently (`Promise.all`) | **Both committed; the revocation was sequenced first** (Lender A's participant: 278, then 279); 1 active lock, 0 disclosures |

Informees of the race transactions: the revocation reached participant2, participant3 and participant5 (the verifier
signs the disclosure, so it learns of the revocation); the activation reached sandbox, participant2 and
participant3 only (the verifier is not informed of the pledge).

So the precheck narrows the window but does not close it: a revocation committed after the API's ACS read and before
the activation commits does not stop the activation. A direct ledger submission that skips the API is not stopped
either. The Daml model was not changed (task scope); see daml-model.md §8.2 and `docs/limitations.md`.

## Findings

- **F1. Terms stay with the borrower and the selected lender.** No principal, term text or legal ref in any stream of
  the registrar, governance, seats, dealer, verifier, Lender B or auditor, nor on the participants that host only
  them. The valuation stays on Lender A's participant.
- **F2. The registrar witnesses the archive of the activation authorization.** `Control_Activate` consumes the
  `PledgeActivationAuthorization` inside the registrar-co-signed control's choice, so the registrar receives the
  exercised `Archive` event (template, contract id, acting lender and borrower, empty argument). It carries no terms
  and no create argument. Not listed in the earlier §5 text; recorded there now.
- **F3. Fetch-only informees.** For `VR_AcceptAssignment` and `VR_IssueAttestation` the registrar's and governance's
  participant takes part like a node hosting a signatory (3 offsets per transaction; the registrar signs the fetched
  config, governance the fetched accreditation) but exposes no event or transaction to any Ledger API user. Its
  operator can see that and when such a transaction happened (offsets move), not, through the Ledger API, what it
  contained. Lender B's and Lender A's participants, observers of the fetched config, take no part.
- **F4. The operator view names informees on other participants.** A `CanReadAsAnyParty` user sees, per event, the
  party ids of all informees, including parties hosted elsewhere. For created contracts these are the stakeholders
  already named in the payload.
- **F5. Directory contracts reach every directory member.** Lender B's participant receives `CollaraConfig` and
  `VerifierStatusMirror`: the directory party list (registrar, verifier, Lender A, Lender B), the governance party, the
  suspension policy and the verifier's status. No case, asset or term data.
- **F6. The verifier learns of disclosures and revocations** of its attestation (recipient and case ref), as designed;
  it learns nothing of proposals, activation or release.
- **F7. GovSeat3 received nothing** in this workflow: seats are not observers of `GovernanceRules` and read it as the
  governance party, which works only because the seat users and the governance party are on the same participant.
- **F8. Revocation race confirmed on the ledger** (see above).
- **F9. No cross-participant input failures.** Every step of the seed, the walkthrough and the races found its input
  contracts on the submitter's participant. No observer or explicit-disclosure change was needed.
- **F10. Bootstrap bug, fixed.** `bootstrap.mjs` treated `CANTON_JSON_API_URL` (set in `.env` for the API) as a
  single-participant override, so the IT harness bootstrapped a 5-participant sandbox as one node (all parties on
  `sandbox`). It now uses that variable only when the running sandbox has at most one participant
  (`--json-api-url` still wins). Found by the first privacy run, which the test's 5-participant guard stopped.
- **F11. Gateway reset check, fixed.** `CantonLedgerGateway.submit` checked the participant id of the user's default
  participant instead of the request's `source`. It now checks the participant it submits to
  (`apps/api/src/ledger/gateway.test.ts`). Submissions were already routed by source.

Note on the two failed runs: run 1 hit F10. Run 2 failed 7 of 63 checks, all wrong expectations in the test, not
privacy failures: it expected all five participants to submit (Lender B and the auditor never do), expected
operator-view witness lists to name hosted parties only (F4), and expected every assigned offset to carry a visible
event (F3). The checks were corrected to assert what holds and to record the rest.

## What this does not show

- **One operator, one machine, one JVM.** All five participants, the sequencer and the mediator run in one process
  that one person controls. This is not independent infrastructure. What the sequencer and the mediator learn
  (metadata, encrypted views, timing) was not examined.
- **Ledger API only.** The claims are about what Ledger API users of each participant can read, including a
  `CanReadAsAnyParty` operator user. A participant's own stores, logs and the views it decrypts while confirming
  (for example the fetched contracts of a transaction it validates) were not inspected.
- **Not Splice LocalNet, and not DevNet, TestNet or MainNet.** Not deployed to a Canton Network.
- **One fixed workflow, twice.** Not covered: share revocation, consent withdrawal, verification grants created through
  the API (`PackageShare` with purpose `VERIFICATION`), supersession and revocation of attestations, governed
  add/suspend verifier and `Mirror_Sync`, information-request rounds, declines and withdrawals, audit grant revocation.
  The unsynchronised race ran once.
- **ACS snapshots** per party were not compared separately (update streams only).
- **The API and read model** ran on the 5-participant ledger only as far as this walkthrough needed (projection from
  all five participants into one database). The normal integration suite still runs on one participant.
- **Not changed:** the Daml model (the race is documented, not fixed), Tier A governance, HMAC ledger auth, in-memory
  state.
